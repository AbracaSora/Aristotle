## 已确认的实现偏差

### 1. 管理员参数配置没有作用到真实模型

关联 FR-7.1、NFR-P-04。

管理员页面保存的是 `SystemSetting.provider` 中的 mock 参数。真实适配器从环境变量读取超时、重试和额度；仅 `mode=disabled` 已用于阻断真实调用，不能将这一点扩大成全部配置已打通。

隔离复现结果：

| 参数 | 管理 API 保存成功的值 | 随后真实适配器读取的值 |
| --- | --- | --- |
| 单次超时 | 1 秒 | 30 秒 |
| 自动重试 | 1 次 | 0 次 |
| 总任务预算 | 2 秒 | 不读取该设置 |
| 日调用上限 | 3 次 | 200 次 |

代码：[管理设置](../../code/backend/aristotle_backend/flow_routes.py) 660–680 行、[真实配置读取](../../code/backend/aristotle_backend/providers.py) 57–89 行。应统一真实服务配置来源、有效配置展示及变更审计；密钥仍由后端安全保存。

### 2. 真实调用配额与需求的数值、时区、范围不同

关联 NFR-P-04。

需求默认每试用账号 100 次/日、内容标注全局 200 次/日，按 Asia/Shanghai 自然日重置。当前真实适配器按 UTC 零点计数，每用户上限硬编码为 `min(60, 全局上限)`，embedding、标注和解释共同占全局额度。超额提示也未给出恢复时间。

代码：[额度预留](../../code/backend/aristotle_backend/providers.py) 94–113 行。已有 PostgreSQL 原子预留与重试计数，但原子性通过不代表配额业务口径符合需求。

### 3. 标注输入没有完整落实已设计的契约

关联 FR-3.2、FR-3.4、功能规范第 4.2 节。

已实现真实请求、六类标签、结构校验和人工审核门禁。但拦截实际构造的兼容请求后，题目输入仅有：

```text
answer, explanation, options, prompt, question_id, question_version
```

缺少需求明确规定的知识点和规则版本。系统提示采用六类简短定义，尚未把原有完整分类口径作为独立、版本化的规则包落实；保存候选时又将提示版本常量同时用作规则版本。需要补齐输入、规则内容及对应追踪字段，不能以一次返回合法标签代替契约核对。

代码：[标注输入与提示](../../code/backend/aristotle_backend/model_jobs.py) 86–140 行。隔离复现使用本地 MockTransport，未发送真实题目或调用供应商。

### 4. 65 秒预算尚未成为整个任务的统一期限

关联 FR-7.1、NFR-R-02。

当前计时从每次 `request_model()` 开始；索引任务按每批 8 个片段反复调用 embedding，每批重新取得预算。worker 没有统一的排队加执行截止时间。因此不能保证一个多批次任务在总计 65 秒内结束；这项结论来自代码控制流，本次未做真实长时间调用实验。

代码：[单次请求预算](../../code/backend/aristotle_backend/providers.py) 134–160 行、[索引分批循环](../../code/backend/aristotle_backend/retrieval.py) 144–201 行、[worker](../../code/backend/aristotle_backend/model_jobs.py)。应把任务截止时间贯穿排队、各批次和重试，再做预算边界测试。

## 教育学定位是否落实

核心边界与原设计一致：先修图决定可继续学习的知识，布鲁姆标签决定题目认知活动；状态由多个不同题目的作答证据推导；理解/应用等维度不相互外推；阅读和模型解释不增加掌握证据；困难后可回看资料并用其他题目复测。模型候选必须审核，LLM 不判分、不发布内容、不直接写学习状态。

目前实现的是需求允许的可解释规则基线。完整知识空间状态族、概率诊断和经验证的测量效度尚未实现，但不能把“没有概率模型”单独算作原 P0 未达标；同样不能把已有先修 DAG 称为完整知识空间理论落地。首版也不要求多智能体或由 LLM 接管推荐决策。
