# Aristotle 408 项目问题定义与产品描述

## 1. 产品描述

Aristotle 408 面向备考计算机 408 的大学生，计划结合知识空间理论诊断薄弱点，利用 LLM 为题目提出布鲁姆认知标签，经人工审核后用于学习设计和反馈建议。不同于以固定题库刷题为主的方式，产品将个人讲义、短关卡与作答证据结合，帮助学生确定下一步学什么、如何从理解走向应用与分析，并持续调整复习路径。

项目由软件工程实践课程团队开发，首批计划邀请 30—50 名学生试用。团队将依次完成分析、设计、开发和测试，拟于 2026 年 12 月发布首版，并根据试用反馈持续迭代。

当前仍处于需求分析与方案设计阶段，以下均为产品规划。首版限定为数据结构部分章节，主要认知目标为记忆、理解、应用、分析；评价与创造活动、复杂主观题自动评分等不纳入首版。详细范围、验收场景和质量目标分别见[功能需求规范](functional_spec.md)与[非功能需求规范](nonfunctional_spec.md)。

| 项目要素 | 描述 |
| --- | --- |
| 产品名称 | Aristotle 408 |
| 产品类别 | 面向计算机 408 备考的自适应学习 Agent |
| 目标用户与规模 | 备考计算机 408 的大学生，首批计划邀请 30—50 人试用 |
| 核心问题 | 用户难以准确识别知识薄弱点和应用、分析等练习缺口，固定复习路径难以适应个人表现变化 |
| 用户价值 | 帮助学生明确复习重点，将有限时间集中用于查漏补缺，减少盲目选题和重复复习 |
| 核心方案 | 知识状态诊断、LLM 候选认知标注与人工审核、按知识点和认知目标推荐、个人讲义与短关卡反馈 |
| 差异化特性 | 将个人资料、知识先修关系与认知活动目标结合，使学习路径和巩固或提升建议随作答证据调整 |
| 团队背景 | 软件工程实践课程团队 |
| 首版发布时间 | 计划于 2026 年 12 月发布 |

## 2. 工程问题定义：5W1H

**核心工程问题：如何根据学生的学习与作答证据，结合知识先修关系和经审核的题目认知标签，持续诊断知识状态，并将结果转化为有明确认知目标、可执行且可调整的复习路径？**

| 维度 | 问题分析 |
| --- | --- |
| What：什么问题 | 学生能够看到刷题结果，却未必能据此判断知识缺口，也不清楚练习要求的是记忆、理解还是应用、分析；统一的练习安排难以匹配个人表现。 |
| Why：为什么解决 | 408 涉及数据结构、计算机组成原理、操作系统和计算机网络，知识点多且存在关联。薄弱点不清容易造成复习重点偏移；以固定题库和顺序刷题为主的方式，难以持续回答个人“下一步学什么”的问题。 |
| Who：谁受影响 | 备考计算机 408、希望根据自身基础安排复习的大学生，尤其是已有个人讲义但缺少明确查漏补缺路径的学生。首批试用规模为 30—50 人。 |
| Where：在哪里发生 | 问题发生在备考过程中的自主复习、练习反馈和后续学习安排环节，贯穿学生从阅读讲义到练习巩固的学习过程。 |
| When：何时发生 | 开始复习但不了解自身基础、完成练习后不清楚错误对应的知识缺口，或掌握程度变化而原有计划未及时调整时，问题尤为突出。 |
| How：如何度量 | 分别评测 LLM 标签与人工参考的一致性，以及独立测评中的知识诊断和前后测表现；记录选任务耗时、关卡完成情况与认知建议反馈。具体口径见第 4 节。 |

## 3. 痛点与解决方案映射

| 用户痛点 | 解决方案 | 预期价值 |
| --- | --- | --- |
| 知道题目做错，却不清楚哪些知识没有掌握 | 结合知识空间理论，利用知识点及其先修关系和作答表现估计掌握状态，定位待巩固的知识点 | 将零散错题转化为明确的复习重点 |
| 练习只见对错，不清楚是在记概念还是练应用与分析 | LLM 依据解题过程提出布鲁姆标签并经人工审核，用于关卡目标、选题和反馈；结合多题证据提出巩固或提升建议 | 让学生理解任务的认知要求及下一步应练什么 |
| 复习路径固定，难以跟随个人进度变化 | 根据最新掌握状态推荐学习内容与练习，并在完成学习后更新后续路径 | 减少对已掌握内容的重复投入，优先补足知识缺口 |
| 个人讲义与练习安排脱节 | 支持上传个人讲义，将讲义内容与相关知识点及学习任务关联 | 将已有学习资料纳入个人复习过程 |
| 复习任务较大，难以明确每次学习的目标 | 采用多邻国式短关卡，将内容学习与练习组织为较小的学习单元 | 让每次学习有清晰目标，并及时获得反馈 |

上述痛点和预期价值是项目的初始假设，需要在用户调研及首批试用中验证。对同类工具的比较限定于“以固定题库刷题为主”的使用方式，不代表所有备考产品都缺少自适应能力。

布鲁姆标签描述题目的认知要求，不等于题目难度，更不能直接当作学生能力等级。知识空间用于约束知识之间的可学习路径，认知标签用于描述任务目标；学生表现须由多题证据支持，不因答对一道“分析”题就认定具备稳定分析能力，也不强迫全部学习按六个层级依次通关。模型候选首版均需人工审核，置信度不作为自动发布依据。

## 4. 效果评估方式

首批试用围绕“能否识别薄弱点、能否指导下一步学习、能否帮助补足缺口”开展评估。以下为拟采用的指标，标签质量及软件质量的初始验收目标已列入[非功能需求规范](nonfunctional_spec.md)，待课程评审和测量验证；学习效果基线仍需实测，当前不将预期收益视为已验证结果。

| 评估目标 | 指标与测量方式 |
| --- | --- |
| 诊断是否有效 | 使用未参与诊断的独立测评题，比较系统判断的掌握状态与测评结果，统计一致率；测评题的知识点对应关系需经过人工核验。 |
| 题目认知标签是否可信 | 至少 100 道首版题目经两名评审者独立标注和分歧裁定，比较人工修订前的 LLM 主标签，报告整体一致率、分层召回率、失败率和混淆矩阵；详见 NFR-Q-01。 |
| 是否帮助补足薄弱点 | 对薄弱知识点安排知识范围、认知标签分布和难度相近的前后测，统计正确率变化（百分点），避免重复原题；证据不足的认知维度单独报告，不外推为总体认知升级。 |
| 是否降低学习安排成本 | 在相近复习任务下，记录用户自行选择与使用推荐时确定下一步学习任务所需的时间，比较中位数。 |
| 短关卡是否便于完成 | 记录关卡完成率（完成次数 / 开始次数）及完成时长，结合中途退出原因判断任务长度是否合适。 |
| 推荐是否符合用户需要 | 收集学生对推荐内容相关性、复习重点和认知目标清晰程度的评分与反馈，并检查是否理解标签与自身能力的区别，定位不合适的建议。 |

试用报告应同时记录实际参与人数、有效样本数和试用周期。标签质量评测与学习收益评估必须分开：模型标签准确不代表教学有效。前后测变化用于观察初步效果，不能仅凭小规模试用直接推断考试成绩提升、长期学习收益或认知能力的因果提升。

## 5. 交付计划与主要里程碑

首版计划于 2026 年 12 月发布；各阶段具体起止日期将在团队排期中细化。

| 阶段 | 主要工作 | 阶段交付物 |
| --- | --- | --- |
| 分析 | 调研目标用户，验证痛点，明确首版知识范围、功能边界和评估指标 | 问题定义、需求规格及验收标准 |
| 设计 | 经课程评审确认功能分解与领域模型，细化知识状态、认知标注及审核、推荐流程与交互 | 系统设计文档、标注规则与交互原型 |
| 开发 | 实现讲义上传、LLM 标签与审核、诊断、按认知目标选题、短关卡及反馈记录 | 可运行的首版候选系统 |
| 测试 | 验证完整学习流程、标签质量、模型失败降级与 URPS 指标，独立评估初步学习效果 | 测试报告、标签评测与缺陷修复记录 |
| 发布 | 于 2026 年 12 月发布首版，邀请 30—50 名目标用户试用 | 首版产品与试用安排 |
| 迭代 | 收集试用数据和反馈，改进诊断、推荐及关卡体验 | 试用评估报告与后续迭代计划 |
